ate — App de Gestão para Artesãos

Apresentação final · ~15 min · Disciplina de Desenvolvimento Mobile (6 meses)

  • Do pedido no WhatsApp à obra entregue — tudo num só lugar
  • Offline-first, com regra rígida: sem foto, sem concluir

Produto de portfólio/aprendizado — sem fins comerciais · 1 usuário por negócio no MVP

02/14O problema

  • Pedidos espalhados: Instagram, WhatsApp, telefone, presencial
  • Controle informal: papel, memória, fotos soltas no celular
  • Sem visão da produção: o que está a fazer, fazendo, feito?
  • Estoque de feira no escuro: levar o quê, quantas unidades?
  • Preço de material sem histórico → compra no chute

03/14Quem usa

  • Artesão independente — esculturas em madeira, feiras de rua
  • Letramento digital básico: usa redes sociais, nada profissional
  • Exige UX guiada: labels explícitos, confirmações visuais claras
  • Trabalha sem internet na feira/oficina → app não pode travar
  • Estende-se a artesãos do mesmo ramo com a mesma dor

04/14A solução — visão geral

  • Em 1 frase: unificar pedidos, produção e estoque num app móvel offline-first.
  • Kanban de pedidos (A Fazer / Fazendo / Feito)
  • Estoque de obras únicas + em série · histórico de preços
  • Cadastro rápido de cliente + pedido na feira · mapa de eventos
  • Sync automático com Supabase quando a rede volta

05/14Fluxo central de uso

  • Pedido chega por qualquer canal → registrado num só Kanban
  • Arrasta o card: A Fazer → Fazendo → Feito
  • Diferencial: Fazendo → Feito exige foto da obra pronta (sem bypass)
  • Foto gera histórico visual e comprovante de entrega

08/14Offline-first — por que e como

  • Por que: feira/oficina sem internet — app precisa funcionar sempre
  • Tudo grava local primeiro: SQLite + status_sync = 'pendente'
  • Fila de sync (FilaSync) esvazia em background ao voltar a rede
  • Imagens: comprime → FileSystem → Storage; depois upsert no banco
  • Conflitos: vale o server timestamp (Supabase), nunca o relógio local

10/14Escopo do MVP — fronteiras

Dentro da v1

  • Kanban + foto rígida · clientes + pedidos
  • Estoque única/série · preços · mapa com pins
  • Offline-first + upload de imagens

Fora da v1

  • Multi-usuário, push, calendário → v1.1
  • Marketplaces, relatórios, exportação → v2

11/14Stack tecnológica

  • Expo / React Native (iOS + Android) + Expo Router (tabs + stacks)
  • SQLite local + FileSystem (imagens comprimidas) · Supabase (Auth/DB/Storage)
  • Clean Architecture + DDD: domain puro, sem importar banco/UI
  • TDD em 3 fases: entidades → use cases (mocks) → repositórios/SQLite
  • Cabe no Free tier: < 30 obras/ano, sem paginação no MVP

12/14Rastreabilidade e qualidade

  • 28 RFs + 12 RNFs, todos mapeados a UCs (tabela UC ↔ RF §2.3)
  • UCs → BCE (boundary/control/entity) → sequência → teste
  • Ex.: RF05 (foto obrigatória) → UC05 → ConcluirPedidoUseCase → teste sem foto falha
  • RLS por usuário · 1 dispositivo · guards em `Pedido.concluir()` e `Obra.reservar()`
  • Detalhe completo na documentação; aqui só a cadeia de rigor

13/14Próximos passos / roadmap

  • Código na ordem: setup Expo → domain → application → SQLite → UI → Supabase/sync
  • v1.1 (se viável): ajudantes com login, push de eventos, calendário
  • v2: integração Elo7/Etsy (canal enum já prevê), analytics, exportação
  • Métrica de sucesso: arquitetura completa + app funcionando minimamente
